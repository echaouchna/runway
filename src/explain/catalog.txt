# What `runway explain` says about runway.yaml.
#
# A block starts with `@ PATH` (a key, with `<name>` for names you choose, or
# `:topic` for a guide). Then optional `title:`, `type:`, `default:`,
# `group:` (to group a service key), `docs:` (page#anchor), `see:` (related
# keys), `also:` (other words people search for it with, or what it is for:
# `ram, keep warm`), `resolved:` (where the resolved value is, `-` for nowhere), then
# paragraphs (the first one is the summary), `Example:` (indented lines) and
# `Rules:` (`- ` lines). Lines starting with `#` are comments.

@ :start
also: getting started, begin, minimal file, hello world, introduction, tutorial
title: Start here
docs: configuration.md
runway.yaml describes a Cloud Run application: how its image is built, how it runs, who may call it, what it needs (secrets, buckets, a runtime identity), and the stages it is deployed to. `runway plan` shows what a deploy would change; `runway deploy` makes the live project match the file.

A file needs `version`, `app`, `provider` (project and region), at least one stage, and something to deploy: the main `service` (named `<app>-<stage>`), more `services`, or `jobs`.

Browse the keys on the left: each one says what it does, its default, an example and its rules. Keys marked ● are set in your runway.yaml; their values per stage are shown below the explanation.
Example:
  version: 1
  app: hello
  provider:
    project: my-gcp-project
    region: europe-west1
    enable_apis: true             # turn on the APIs it needs
    create_build_resources: true  # and the repository, bucket and build account
  service:
    source: .
    service_account: hello-runtime@my-gcp-project.iam.gserviceaccount.com
    identity: {create: true}
    public: true
  stages:
    dev: {}
    prod:
      service: {min_instances: 1}
Rules:
- Unknown keys are errors (with the list of valid ones): typos never go unnoticed.
- `runway validate` checks the file without credentials; `runway describe --stage S` explains what a stage deploys.

@ :layers
also: override per stage, precedence, inherit, merge, remove an inherited key, environment specific
title: Stages, defaults and precedence
docs: configuration.md#stage-override-precedence
see: stages, defaults, stages.<name>.service
Every stage is deployed from the same file. A stage block changes only what differs: `stages.prod.service.min_instances: 1` keeps everything else from `service`.

Lowest first: `defaults`, `stages.S.defaults`, the service or job, `stages.S.<its block>`, then `--image` on the command line. Scalars are replaced; maps (`env`, `secrets`, `tags`, `volumes`, `sidecars`, `vars`) merge key by key, and `null` removes an inherited key. `identity`, `iap`, `vpc` and `health_check` blocks are replaced as a whole.

The highest layer that sets `image` or `source`/`dockerfile` chooses how the image is made: a stage that sets `image` replaces a top-level source build, and the other way round.
Example:
  service:
    memory: 512Mi
    env: {LOG_LEVEL: info, DEBUG: "1"}
  stages:
    prod:
      service:
        memory: 1Gi          # replaced
        env: {DEBUG: null}   # removed; LOG_LEVEL stays
Rules:
- Setting both `image` and `source` in one block is an error.
- Scalars cannot be removed with `null`, only replaced.

@ :variables
also: interpolation, template, placeholder, substitution, dollar
title: Variables
docs: configuration.md#variables
see: vars, buckets, secrets
`${...}` is replaced in most names: `provider.source_bucket`, `provider.build_service_account`, bucket and secret names, `service_account`, `env` values, `identity`, volume buckets and IAP members.

Available: `${project}`, `${region}`, `${app}`, `${stage}`, `${vars.NAME}`, `${buckets.KEY}` (the name of a declared bucket) and `${secrets.KEY}` (a secret runway creates). `$$` is a literal `$`.
Example:
  vars:
    data_project: my-data-project
  service:
    service_account: "${app}-runtime@${project}.iam.gserviceaccount.com"
    env:
      DATA_PROJECT: "${vars.data_project}"
Rules:
- Unknown variables are validation errors.

@ :names
also: naming, service name, labels, ownership, managed by runway
title: Names of what runway creates
docs: configuration.md#several-services-jobs-and-schedules
see: app, services, jobs
The main service is `<app>-<stage>`; named services and jobs are `<app>-<name>-<stage>`, and so are schedules. Images go to the package `<app>` (main service) or `<app>-<name>`.

Everything runway creates carries the labels `managed-by=runway`, `runway-app` and `runway-stage` (or a marker in its description): runway never changes nor deletes what it does not own.
Rules:
- Service names are at most 49 characters, job names 63.
- A service and a job cannot share a name, and none can be the app name.

@ version
also: schema version
type: integer
docs: configuration.md
The schema version of the file. Only `1` exists.
Example:
  version: 1
Rules:
- Required.

@ app
also: application name, app name
type: string
docs: configuration.md
see: :names
The application name. It names everything runway creates: the main service is `<app>-<stage>`, named ones `<app>-<name>-<stage>`.
Example:
  app: hello-api
Rules:
- Required: lowercase letters, digits and hyphens, starting with a letter, up to 40 characters.
- Changing it deploys new services under new names (the old ones stay until `undeploy`).

@ vars

Your own variables, used as `${vars.NAME}`. Values may use the built-in variables (`${project}`, `${stage}`…).
Example:
  vars:
    data_project: my-data-project

@ provider
also: google cloud, gcp, where to deploy
type: block
docs: configuration.md
Where the app is deployed (project and region), how images are built (repository, source bucket, build account) and what runway may create for you. A stage can override any of it.
Example:
  provider:
    project: my-gcp-project
    region: europe-west1
    enable_apis: true
    create_build_resources: true

The Google Cloud project ID everything is deployed to.
Example:
  project: my-gcp-project

- Required (here or in every stage).

@ provider.region

type: string
resolved: /region
docs: configuration.md
The Cloud Run region, also used by Cloud Build and as the default location of buckets, secrets and the repository.
Example:
  region: europe-west1
Rules:
- Required (here or in every stage).

@ provider.enable_apis
also: enable services, turn on apis, service usage, api not enabled
type: boolean
default: false
resolved: /apis/enable
docs: getting-started.md#let-runway-create-what-it-needs
see: provider.apis
Enable the Google Cloud APIs the configuration needs when they are missing (Cloud Run, Cloud Build, Secret Manager…). Without it, `runway doctor` reports the missing ones.
Example:
  enable_apis: true
Rules:
- Needs `roles/serviceusage.serviceUsageAdmin`.
- APIs are never disabled by runway, not even by `undeploy`.

@ provider.apis
also: extra apis, google apis
type: list of strings
resolved: /apis/extra

Extra APIs runway cannot infer from the file (for example ones your app calls), checked by `doctor` and enabled with `enable_apis`.
Example:
  apis: [telemetry.googleapis.com, translate.googleapis.com]

@ provider.create_build_resources
also: first time setup, build setup
type: boolean
default: false
docs: getting-started.md#let-runway-create-what-it-needs
Create what source builds need when missing: the Artifact Registry repository, the source bucket and the build service account with its roles. The three names then default to `runway`, `<project>-runway-sources` and `runway-build@<project>.iam.gserviceaccount.com`.
Example:
  create_build_resources: true

docs: configuration.md
The Artifact Registry repository (Docker format) built images are pushed to.
Example:
  artifact_repository: applications
Rules:
- Required for source builds, unless `create_build_resources` is true.

@ provider.artifact_location
also: registry location, multi region
type: string
default: provider.region

The location of the repository, when it is not the region (for example a multi-region `europe`).

@ provider.source_bucket

The Cloud Storage bucket the source archive is uploaded to before a build. A name without `gs://`; variables work.

- Required for source builds, unless `create_build_resources` is true.

@ provider.build_service_account
also: cloud build account, build identity
type: string
default: runway-build@<project>.iam.gserviceaccount.com (with create_build_resources)
docs: permissions.md
The account Cloud Build runs as: it reads the source archive, pushes the image and writes build logs.
Example:
  build_service_account: "builds@${project}.iam.gserviceaccount.com"
Rules:
- Required for source builds, unless `create_build_resources` is true.

@ provider.impersonate_service_account
also: impersonation, act as, delegation, token creator
type: string
resolved: /impersonate
docs: ci-cd.md
Make every API call as this service account (your credentials need `roles/iam.serviceAccountTokenCreator` on it). `SA` or a delegation chain `DELEGATE,...,SA`.
Example:
  impersonate_service_account: deployer@my-gcp-project.iam.gserviceaccount.com
Rules:
- `--impersonate-service-account` on the command line wins.

@ provider.tags
also: organization policy, org policy, resource manager tags
type: map
resolved: /project_tags
docs: how-it-works.md
see: service.tags, service.bootstrap
Resource Manager tags bound to the project before anything is created, then awaited until effective: for organization policies that only allow something (like `ingress: all`) on tagged projects.
Example:
  tags:
    "123456789012/allowIngressAllForCloudRun": allow-ingress-all
Rules:
- Keys are `ORG_OR_PROJECT_ID/key`.
- A stage map replaces the inherited one.

@ service
also: main service, web app, api, container, http server
type: block
docs: configuration.md
see: defaults, services, :layers
The main service, named `<app>-<stage>`. Its keys are the ones of every service: how the image is made, resources, access, identity, secrets, storage, networking, containers and domains.
Example:
  service:
    source: .
    port: 8080
    memory: 1Gi
    public: true
    service_account: hello-runtime@my-gcp-project.iam.gserviceaccount.com
Rules:
- Optional when `services` or `jobs` exist.

@ service.source
also: build from source, build from code, folder, directory, cloud build
type: path
default: . (when there is no image)
group: Build and image
resolved: /artifact
docs: configuration.md
The folder to build the image from, relative to runway.yaml. runway uploads it (minus `.runwayignore`/`.dockerignore`), builds it with Cloud Build and skips the build when neither the source nor a base image changed.
Example:
  source: apps/web
Rules:
- Not with `image` in the same block.
- Services and jobs with the same build (folder, Dockerfile or builder) share one image, built once.

@ service.dockerfile
also: docker, dockerfile path, containerfile
type: path
default: Dockerfile, if present (else buildpacks)
group: Build and image
resolved: /artifact
docs: configuration.md
The Dockerfile, relative to `source`. Without one, Google Cloud buildpacks build the image.
Example:
  dockerfile: docker/Dockerfile.prod

@ service.builder
also: buildpacks, builder image, without dockerfile
type: image
default: gcr.io/buildpacks/builder:latest
group: Build and image
resolved: /artifact
docs: limitations.md
Build with buildpacks using this builder image, even if there is a Dockerfile.
Example:
  builder: gcr.io/buildpacks/builder:google-22
Rules:
- The default is a moving tag: each new digest rebuilds. Pin it for reproducible builds.

@ service.rebuild
also: force build, build cache, always rebuild
type: on-change | always
default: on-change
group: Build and image
docs: configuration.md
When to rebuild: `on-change` when the source or a base image changed, `always` on every deploy (like `--force-build`).
Example:
  rebuild: always

@ service.image
also: prebuilt image, existing image, docker image, container image, image tag, digest
type: image reference
group: Build and image
resolved: /artifact
docs: configuration.md
Deploy an existing image instead of building one. A tag is resolved to its digest at deploy time when the registry allows it, so a plan shows exactly what runs.
Example:
  image: europe-west1-docker.pkg.dev/my-gcp-project/apps/hello:1.2.3
Rules:
- Not with `source`/`dockerfile`/`builder` in the same block.
- `--image` on `plan`/`deploy` overrides it.

type: list of strings
default: the image's entrypoint
group: Build and image

The entrypoint of the app container.

@ service.args
also: arguments, flags, parameters
type: list of strings
default: the image's arguments

The arguments of the entrypoint.

@ service.port
also: listen port, http port
type: integer
default: 8080
group: Resources and scaling
docs: configuration.md
The port the app listens on; Cloud Run sends requests there and sets `$PORT`.
Example:
  port: 3000

@ service.cpu
also: vcpu, processor, cores, compute
type: number or string
default: 1
group: Resources and scaling
docs: configuration.md#cpu-sandboxes-networking-and-cloud-sql
vCPUs per instance: 1, 2, 4, 6 or 8, or between 0.08 and 1 (also `"500m"`).
Example:
  cpu: 2
Rules:
- Below 1 needs `concurrency: 1`, request-based billing and gen1.
- Jobs need at least 1.

@ service.memory
also: ram, memory limit, out of memory, oom, gigabytes
type: string
default: 512Mi
group: Resources and scaling
docs: configuration.md
Memory per instance, from 128Mi to 32Gi.
Example:
  memory: 1Gi
Rules:
- gen2, sandboxes, instance-based billing and jobs need at least 512Mi.
- More memory needs more CPU: above 4Gi at least 2 CPUs, above 8Gi 4, above 16Gi 6, above 24Gi 8.

@ service.timeout_seconds
also: request timeout, slow requests, long requests, deadline, 504
type: integer
default: 300
group: Resources and scaling
docs: configuration.md
How long a request may take, from 1 to 3600 seconds.
Example:
  timeout_seconds: 60
Rules:
- For a job, see `jobs.<name>.timeout_seconds` (a task timeout).

@ service.concurrency
also: requests per instance, parallel requests, simultaneous requests, throughput
type: integer
default: 80
group: Resources and scaling
docs: configuration.md
Requests one instance handles at once, from 1 to 1000.
Example:
  concurrency: 20

@ service.min_instances
also: keep warm, always on, cold start, idle instances, minimum instances, scale to zero
type: integer
default: 0
group: Resources and scaling
docs: configuration.md
Instances kept running even without traffic (no cold starts, billed while idle).
Example:
  min_instances: 1
Rules:
- At most `max_instances`. runway warns that warm instances are billed.

@ service.max_instances
also: autoscaling limit, autoscale, scale out, cap cost, maximum instances, limit instances
type: integer
default: 10
group: Resources and scaling
docs: configuration.md
The most instances Cloud Run may start: a cap on cost and on load on what the app calls.
Example:
  max_instances: 50

@ service.billing
also: cpu always allocated, cpu throttling, background work, background tasks, pricing, cost
type: request-based | instance-based
default: request-based
group: Resources and scaling
docs: configuration.md#cpu-sandboxes-networking-and-cloud-sql
`request-based` gives CPU only while requests are handled; `instance-based` gives it for the instance's whole life (background work, exporters) and is billed that way.
Example:
  billing: instance-based
Rules:
- `instance-based` needs at least 1 CPU and 512Mi.

@ service.startup_cpu_boost
also: faster startup, cold start, slow start, boost
type: boolean
default: false
group: Resources and scaling
docs: configuration.md#cpu-sandboxes-networking-and-cloud-sql
More CPU while instances start and for 10 seconds after: faster cold starts, billed.
Example:
  startup_cpu_boost: true

@ service.execution_environment
also: gen1, gen2, generation, linux compatibility, gvisor
type: gen1 | gen2
default: Cloud Run chooses
group: Resources and scaling
docs: configuration.md#cpu-sandboxes-networking-and-cloud-sql
`gen2` gives full Linux compatibility and faster CPU and network, with slower cold starts; `gen1` starts faster.
Example:
  execution_environment: gen2
Rules:
- gen2 needs at least 512Mi; gen1 cannot mount Cloud Storage volumes.

@ service.sandbox
also: untrusted code, isolation, ai generated code, headless browser
type: boolean
default: false
group: Resources and scaling
docs: configuration.md#cpu-sandboxes-networking-and-cloud-sql
Cloud Run sandboxes (preview): the app can run untrusted code (AI-written code, user scripts, a headless browser) in isolated sandboxes with the `sandbox` command, for example `sandbox do -- python3 script.py`. Sandboxes have no network, environment or secrets unless the app passes them.
Example:
  sandbox: true
Rules:
- Implies gen2 (gen1 is rejected), so at least 1 CPU and 512Mi.
- Sandboxes share the container's CPU and memory.

@ service.public
also: unauthenticated, allow unauthenticated, allusers, anonymous, open to the internet, private service, who can call
type: boolean
default: false
group: Access and networking
docs: configuration.md
Anyone may call the service (the `allUsers` invoker binding). Private services need an identity token with `roles/run.invoker`.
Example:
  public: true
Rules:
- Organizations with Domain Restricted Sharing refuse `allUsers`: keep the service private or use `iap`.

@ service.ingress

group: Access and networking

Where requests may come from: anywhere, only from inside the VPC/project, or also through a Google Cloud load balancer.
Example:
  ingress: internal-and-cloud-load-balancing

- With `domains` behind a load balancer, `internal-and-cloud-load-balancing` forces traffic through it.

@ service.iap
also: identity aware proxy, google login, sign in, sso, employees only, authentication

    members: [group:finops@example.com, user:alice@example.com]
Rules:
- `iap.members` is the complete list: members added elsewhere are removed by the next main deploy.
- A stage block replaces the inherited one.

Who may pass IAP (`roles/iap.httpsResourceAccessor`): `user:`, `group:`, `domain:` or `serviceAccount:` principals.
