How it works

      
Describe it once. Re-run forever.

      
Scroll through a deploy. Each step reads the live project first and changes only what differs, in dependency order, so an interrupted run simply resumes.

    

    

      

        

          
runway.yaml


version: 1
app: hello
provider:
  project: my-gcp-project
  region: europe-west1
  enable_apis: true
  create_build_resources: true
secrets:
  api-key: { adders: [group:devs@example.com] }
service:
  source: .            # Dockerfile or buildpacks
  service_account: "hello-run@${project}.iam.gserviceaccount.com"
  identity:
    create: true
    roles: [{ role: roles/storage.objectUser, bucket: my-data }]
  secrets: { API_KEY: { secret: "${secrets.api-key}" } }
  health_check: { path: /healthz }
  iap: { members: [group:devs@example.com] }
stages:
  dev: {}
  prod: { service: { min_instances: 1 } }

        

      

      
    
        
  1. 01
    APIs
    Enables what the file needs (Cloud Run, Cloud Build, Secret Manager…), or runway doctor lists them.
    2. 
        
  2. 02
    Build resources
    The image repository, the source bucket (30-day cleanup) and a build account with exactly the roles it needs.
    3. 
        
  3. 03
    Secrets
    Created empty, fillable by the people you list. The deploy stops with the exact gcloud command until they have a value.
    4. 
        
  4. 04
    Identity & grants
    A runtime account per app, service or job, with roles on exactly one bucket, dataset, secret or project. Removed access is revoked.
    5. 
        
  5. 05
    Build
    Cloud Build, content-addressed: the same source and base images are never built twice.
    6. 
        
  6. 06
    Roll out & wait
    Pinned digest, probes, scaling. runway waits until the revision is healthy, and shows why when it is not.
    7. 
        
  7. 07
    Traffic & access
    Public, private, IAP or restricted ingress; previews, canaries and promotions without revision churn.

Releases & promotion

      
Release exactly what you tested.

      
dev builds. UAT promotes what dev serves. On a git tag, prod promotes the image UAT ran for that exact commit, publishes it to your release registry and tags it: same digest, no rebuild, no guess.

    

    

      
      
sha256:9f2c…

      
dev
Builds
from main, commit a1b2c3
src-5ce4…

      
uat
Promotes
promote: {from: dev}
1.2.0-RC2

      
prod
Releases
promote: {from: uat, commit: checkout}
1.2.0

    

    

      
Evidence, not guesses. What a stage serves is read from its one revision with all the traffic, with the commit and release that revision records.

      
Your registry, your paths. Publish to LOCATION-docker.pkg.dev/PROJECT/REPO/team/agent:1.2.0, as a dedicated push account.

      
Safe to re-run. A version is never moved to another image; a re-run keeps what the stage already serves.

CI/CD

      
The same command in your pipeline.

      
Workload Identity Federation, a container image, JSON output, stable exit codes, and a lease so two pipelines never step on each other.

      
    
        
  • Branches get a preview URL, merged ones are pruned
    • 
        
  • Tags release, with the version checked against your changelog
    • 
        
  • An older commit is refused unless you mean it (--allow-older)
    • 
        
  • Impersonate a deployer; push images as another account
    • 
      

    

    

      
.gitlab-ci.yml


preview:
  script: runway deploy --preview "$CI_COMMIT_REF_NAME"
  rules: [{ if: $CI_COMMIT_BRANCH != $CI_DEFAULT_BRANCH }]

release:
  script: runway deploy --stage prod --tag
  rules: [{ if: $CI_COMMIT_TAG }]

prune:
  script: runway preview prune --yes
  rules: [{ if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH }]
